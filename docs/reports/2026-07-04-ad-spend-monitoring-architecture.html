核心結論 摘要

系統已完成 80%——異常規則引擎、分析引擎、預算配速頁都已上線，缺口只有「排程主動檢查＋推播到你眼前」這一層。建議主 app 留在 Zeabur，加一個 Cloudflare Worker 當監控哨兵，每天定時檢查並推 LINE 摘要。

結論：走「選項 A：Zeabur 主 app ＋ Cloudflare Worker 哨兵」。改動最小、風險最低、一個下午可上線，同時滿足 Cloudflare 的需求。通知管道已定案用 LINE（Messaging API）。
判斷：每天推播只放「要不要行動」的訊號（3-5 個數字＋紅黃綠），細節留在網頁。推播塞滿數據，三天後就不會再看了——推播是門鈴，網頁是門。
警告：LINE Notify 已於 2025 年 3 月底終止服務，網路上大量舊教學已失效。要走 LINE 只能用 Messaging API（官方帳號 push），免費額度 200 則/月，推給自己綽綽有餘。

現況盤點 已有資產

以下都已存在於 repo 並有測試覆蓋，監控系統不必從零蓋：

  • 異常規則引擎：AlertRule／AlertNotification 資料表 ＋ /api/alerts/check（可自訂指標、閾值、變化率條件）
  • 分析引擎：預算異常、素材疲勞、成效判讀（src/lib/analysis/）
  • 預算配速頁：/initiatives 帳號卡雙向三色配速 ＋ 手動月預算（2026-07-03 剛上線）
  • 應用內通知：通知鈴鐺 ＋ 瀏覽器推播（Web Notifications）
  • 排程基礎：src/lib/cron/ 已有 scheduler／job-executor（目前服務 Notion 同步）
缺口：通知只在打開網頁時才看得到。沒有伺服器端排程主動跑檢查，也沒有把結果送出 app 之外（LINE／Email）。

Cloudflare 部署選項 三選一

架構圖（選項 A，建議）

  • 監控系統
    • Cloudflare Worker 哨兵
      Cron Triggers：每天 08:30 ＋ 盤中每 4h
      • 打 app API
        /api/alerts/check ＋ /api/digest/daily（CRON_SECRET 驗證）

三選項比較

選項 做法 優點 代價／風險 工期
A 建議 Zeabur 主 app 不動，Cloudflare Worker（Cron Triggers）負責排程檢查與 LINE 推播 主 app 零遷移風險；Worker 約 150-200 行；免費額度綽綽有餘 多一個小服務要管 一個下午
B 全站搬 Cloudflare：OpenNext adapter ＋ Hyperdrive 連外部 Postgres 平台統一、全球 edge Next 16 ＋ Prisma 7 在 Workers 上屬前緣組合，AES-256-GCM 加密、pg adapter 相容性要逐一驗證；DB 仍在外部 2-4 天＋踩坑風險
C GitHub Actions 排程打現有 API，先驗證日報內容價值 半天搞定、零新基建 沒用到 Cloudflare；Actions 排程尖峰可延遲 3-15 分鐘 半天
建議：走 A。除非本來就想離開 Zeabur，否則 B 的投報比低；C 適合當 A 之前的快速驗證，但 A 本身已經夠快，不必多此一舉。
